Título: ADR-001 Elección de PostgreSQL como motor de base de datos

Estado: Aceptado Fecha: 2026-06-16
Decisores: Equipo Escuchify Relacionado: TP6-ArquitecturaDiseño

Contexto

- Se necesita un motor de base de datos relacional para persistir la información del proyecto Escuchify: usuarios, playlists, canciones, métricas de reproducción y datos de streaming.

- Restricciones aplicables: debe ser open source, con licencia permitida para uso comercial, contar con buen soporte para consultas complejas y transacciones ACID, y tener capacidad de manejo de datos geoespaciales.

- Datos de proyecto: el equipo tiene experiencia previa con PostgreSQL y MySQL; se prioriza madurez, comunidad activa y extensibilidad.

Decisión

- Se decide utilizar PostgreSQL como motor de base de datos relacional principal del proyecto Escuchify.

- Alcance: cubre el almacenamiento de todos los datos transaccionales del sistema (usuarios, playlists, canciones, métricas). No cubre almacenamiento en caché ni sesiones temporales, que podrán manejarse con herramientas como Redis.

Alternativas consideradas

- MySQL: ampliamente usado, fácil de configurar. Contras: menor soporte para datos geoespaciales, extensiones más limitadas, rendimiento inferior en consultas analíticas complejas.

- SQLite: liviano, sin configuración de servidor. Contras: no soporta concurrencia de escritura, no es escalable, no apto para producción con múltiples usuarios simultáneos.

- MongoDB: esquema flexible, escalabilidad horizontal. Contras: no es relacional, consistencia eventual, el modelo de datos de Escuchify es inherentemente relacional (usuarios-playlists-canciones).

Consecuencias

- Beneficios esperados: cumplimiento ACID, integridad referencial, extensiones como PostGIS para datos geoespaciales, madurez del proyecto, comunidad activa, rendimiento sólido en consultas complejas.

- Costos o riesgos que se aceptan: mayor consumo de memoria y almacenamiento comparado con SQLite, necesidad de administración del servidor de base de datos, curva de aprendizaje para features avanzadas.

- Impacto en operación y equipo: el equipo deberá configurar y mantener la instancia de PostgreSQL, escribir migraciones de esquema y optimizar consultas.

Plan de implementación

- Pasos mínimos: 1) Instalar PostgreSQL en entorno de desarrollo. 2) Diseñar el esquema relacional. 3) Configurar cadena de conexión en la aplicación. 4) Ejecutar migraciones iniciales. 5) Poblar con datos de prueba.

- Dependencias: driver de PostgreSQL para el lenguaje de implementación (ej. pg para Node.js, psycopg2 para Python).

- Métrica de éxito: todas las operaciones CRUD del sistema funcionan correctamente contra PostgreSQL en entorno de desarrollo.

Triggers de revisión

- Cambio en los requisitos que exija un modelo de datos no relacional.

- Problemas de rendimiento no solucionables con optimización de consultas o indexación.

- Necesidad de escalar más allá de la capacidad de una instancia PostgreSQL (sharding, replicación compleja).
